# Remote Skycache network, storage, and cache scheduling research

Research cutoff: 26 October 2026. Planning only; no builds, benchmarks, implementation changes, or network-setting changes were performed. Internal code read from remote-mvp current checkout; measured-result attribution supplied by the independent audit and checked against the current MVP guide. All numerical research results below belong to their authors' workloads, not to Skycache.

## 1. What does the implementation imply should be optimized first?

### Takeaway

The retained-warm result already eliminates downloaded blob payloads and still loses to local Skycache. First separate publication time, full-chunk initial authentication, fine-grained local read/authentication work, and scheduler waits; a network-only optimization cannot explain or fix the warm deficit by itself.

### Cited Findings

- The latest measured product commit is `b368beb0ddde51434ce20c063546047ecccb2a88`; the current HEAD is a later formatting/documentation commit according to the audit. The guide records 612 passing tests and n=3 per measured arm. Minimal medians: local 14.27s, remote empty-retained-cache 45.97s, remote retained-warm 26.17s; toplevel 25.22/54.43/33.78s. These are separate from the earlier synthetic results. [MVP guide, lines 845 onward](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/docs/jsgette/skycache-remote-mvp.md)
- Audit-confirmed interpretation of the same experiment: all six retained-warm runs downloaded zero **blob payload** bytes, reused 1604 chunks / approximately 1.462GB locally, still received control/manifest traffic and uploaded about 10.26MB. All remote timed runs include synchronous publication (5–16 writes). The benchmark used **2GiB transfer / 600s timeout overrides**, unlike defaults 257MiB / 60s. Do not call these measurements WAN tests or default-configuration results. [MVP guide](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/docs/jsgette/skycache-remote-mvp.md)
- `RemoteSkyCache.uploadLocal` (1004–1034) reads each file into fixed chunks of at most 1MiB and waits for `transport.upload` sequentially. `SkyCacheTransport.upload` (325 onward) uses a singleton identity-compressed BatchUpdateBlobs request. The protocol explicitly lists missing capability negotiation, FindMissingBlobs, BatchReadBlobs, and compressed transfer. The reader is already lazy: a demanded range selects intersecting complete chunks. [RemoteSkyCache](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/src/main/java/com/google/devtools/build/lib/skyframe/serialization/local/RemoteSkyCache.java); [Protocol](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/docs/jsgette/skycache-remote-cache-protocol-2026-10-25.md)
- Download coalescing already exists: 1024 striped locks plus separate semaphores for downloads and cached readers. The transport also bounds concurrent RPCs and debits cumulative **active RPC time**: concurrent requests consume budget at the sum of their elapsed times, not merely elapsed wall time. [RemoteSkyCache, 51–59 and 350–450](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/src/main/java/com/google/devtools/build/lib/skyframe/serialization/local/RemoteSkyCache.java); [SkyCacheTransport, 430–489](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/src/main/java/com/google/devtools/build/lib/skyframe/serialization/remote/SkyCacheTransport.java)
- Retained reuse hardlinks and reads the **whole chunk**, verifies its CAS digest, generates 4KiB block hashes, and updates mtime once on this first retained reuse in a session. Subsequent range reads touch an access-ordered synchronized LinkedHashMap, open a FileChannel, perform filesystem/size checks, read block-aligned bytes, and hash each returned 4KiB block. `FileSource.read` and `isCached` scan the chunk list from its beginning. This is code evidence of work, not a claim that any one operation dominates. [RemoteSkyCache, 131–340 and 452–489](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/src/main/java/com/google/devtools/build/lib/skyframe/serialization/local/RemoteSkyCache.java)
- Authentication metadata defaults to 32MiB, with 32 bytes per 4KiB block plus 128 bytes per chunk. Persistent retained storage defaults to 5GiB; collection scans up to 256 prefix directories, sorts entries by mtime, and prunes after close. [RemoteSkyCache, 50–76](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/src/main/java/com/google/devtools/build/lib/skyframe/serialization/local/RemoteSkyCache.java); [RemoteChunkCache, 145–230](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/src/main/java/com/google/devtools/build/lib/skyframe/serialization/local/RemoteChunkCache.java)
- **Peer-reviewed, 20 April 2026:** Qiu/Yang/Harchol-Balter, *Why increasing the hit ratio can hurt cache throughput*, shows hit-path contention can reduce throughput as hit ratio rises. Its principal model is a closed queueing network with fixed concurrency (72 requests/cores), serial cache-maintenance stations, measured service times, analytical throughput bounds, simulation and implementation. It is not a theorem that Skycache has that bottleneck. [Queueing Systems paper](https://link.springer.com/article/10.1007/s11134-026-09986-1)
- **Peer-reviewed, NSDI April 2024:** SIEVE uses inexpensive hit tracking and avoids lock acquisition on its hit path; evaluated across 1559 web-cache traces, with better scalability than its optimized LRU comparator. This supports testing less mutable hit metadata, but its workload and in-memory implementation differ from Skycache's verified filesystem chunks. [SIEVE](https://www.usenix.org/conference/nsdi24/presentation/zhang-yazhuo)
- **Peer-reviewed PVLDB 19(4):549–562, 2025 journal reference / VLDB 2026 conference; arXiv posted 30 August 2026:** *Demystifying and Improving Lazy Promotion in Cache Eviction* reports that Delay-LRU/FIFO reinsertion improve hits per promotion; D-FR/AGE reduce promotions 20–60% in the evaluated workloads. This is stronger support for measuring hit-path maintenance than for choosing a particular replacement algorithm today. [Paper](https://arxiv.org/html/2608.29993v1); [official issue contents](https://www.vldb.org/pvldb/vol19/FrontMatterVol19No4.pdf)

### Inferences

**Proposed experiment order, not changes made:**

1. **P0: attribute the warm deficit.** Add a phase/event design for later implementation: discovery/preparation; retained pin/full hash; cached range read/hash; source-witness validation; deserialization; lock/semaphore waits; local persistence; upload; catalog commit; prune/cleanup. Record both sums and interval-union/critical-path contribution. Sum-of-thread time cannot be subtracted from wall time. Audit the already recorded approximately 790,700 shared-CAS gets / 244.62MB requested values against 1.462GB chunks: the roughly 6x ratio is an aggregate symptom, not a distinct-byte amplification measurement.
2. **P0 diagnostic split:** compare consume-only and consume-plus-publish with the same frozen corpus and source state. This isolates publication and is a benchmark condition, not a proposal to silently remove product publication. Add native defaults beside the 2GiB/600s research configuration; budget fallback frequency is an outcome.
3. **P1 warm work reduction, chosen by measured spans:** reduce redundant range lookups and syscall churn; consider batched/coalesced adjacent reads, a bounded descriptor cache, and prefix-offset indexing for chunk lookup. Compare a sharded/SIEVE-like authentication metadata cache only if monitor contention appears. Keep every returned byte authenticated; do not use persistent mtime as a trust certificate.
4. **P1 publication:** capability-bounded upload batching, a FindMissingBlobs break-even experiment, and bounded parallel preparation/upload. Preserve ordering: chunks successfully stored, bundle uploaded, then existing idempotent catalog commit. Share the existing total byte/time/cancellation limits; avoid concurrency multiplying effective allowed resource use.

At roughly 1MiB/chunk, 1604 chunks need approximately 13MiB of block-hash metadata; that fits the 32MiB authentication budget. Thus an eviction-algorithm rewrite has weak current evidence unless actual eviction/lock counters show trouble. Conversely, mandatory initial full-chunk hashing can read approximately 1.46GB even when network bytes are zero.

A simple publication model is `T_pub ≈ n·r + U/B + T_hash + T_commit` for serialized RPCs, where r is per-call fixed latency and U transmitted bytes. Batching may lower n; parallelism may overlap r; FindMissing lowers U only where digests recur. Each term must be measured, and CPU/I/O overlap means this is not a forecast.

**Proposed gates:** paired wall-time confidence interval excludes no improvement, median improvement at least 5% on the target arm, no greater than 3% regression on protected arms, unchanged correctness/fallback behavior and memory limits. These are suggested engineering thresholds, not observed research results. For attribution, require overlap-aware reconstruction of at least 90% of command time before broad architectural changes.

### Gaps

- No current span attribution proves hashing, monitor contention, filesystem calls, or sequential publication is the dominant warm cost.
- Three observations per arm cannot establish p95/p99 or reliable confidence intervals.
- The 790,700 calls and requested bytes need exact counter semantics, deduplication, and overlap analysis.
- Remote-v2 differences were not independently audited here; the coordinator's audit owns branch/current-state comparison.

## 2. Which recent algorithms can reduce cold transfer and packing cost without changing the trust model?

### Takeaway

First test smaller independently authenticated chunks and stable record-aware layout within the existing envelope. Consider CDC only after measuring cross-version byte stability, and keep compression, deduplication, and demand amplification as separate mechanisms.

### Cited Findings

- Current v1 accepts variable chunk lengths 1–1MiB, limits total chunk references to 32,768 and serialized bundles to 1MiB, and permits at most 4GiB logical closure. The producer chooses fixed 1MiB chunks; the reader already resolves declared variable chunk lengths. A smaller producer chunk size therefore need not intrinsically change the wire format, but the envelope limits can make it infeasible. [SkyCacheProtocol, 17 and 91–92](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/src/main/java/com/google/devtools/build/lib/skyframe/serialization/remote/SkyCacheProtocol.java); [Protocol bounds](//wsl.localhost/Ubuntu/home/jgett/REPOS/bazel-skycache-remote-mvp/docs/jsgette/skycache-remote-cache-protocol-2026-10-25.md)
- **Latest available preprint, 9 October 2026; author reports acceptance at future ICDE 2027:** Gregoriadis et al., *Benchmarking Content-Defined Chunking Algorithms for Data Deduplication*, isolates base CDC from normalization/threshold/caching layers, compares eight algorithms on four workloads, and identifies an AE parameterization error producing 13–39% smaller chunks than intended. Equal nominal parameters are not fair equal-granularity comparisons. Treat acceptance as author-reported; do not call it a published 2027 conference result. [arXiv record and abstract](https://arxiv.org/abs/2610.13704)
- **Peer-reviewed FAST, February 2025:** VectorCDC accelerates hashless CDC boundary search using SIMD and reports substantially faster chunking without changing deduplication savings in its workloads. Its 2026 TOS extension is listed as published February 2026 by the authors' lab; arXiv v2 dated 26 January 2026 says accepted. Byte-scanning acceleration does not establish end-to-end network or Java performance. [FAST paper](https://www.usenix.org/conference/fast25/presentation/udayashankar); [TOS extension](https://arxiv.org/abs/2508.05797); [author publication list](https://wasl.uwaterloo.ca/projects/deduplication/)
- **2026 SeqCDC evidence:** The May 2025 preprint still says “under review”; the current author publication list identifies *Vectorized Sequence-Based Chunking for Data Deduplication* as IEEE TPDS, February 2026, with the published-version manuscript linked. Prefer that updated record when describing status. It is relevant only if CDC CPU cost becomes material after data layout is selected. [Author publication record](https://wasl.uwaterloo.ca/projects/deduplication/); [2026 manuscript](https://cs.uwaterloo.ca/~alkiswan/papers/Vectorized_SeqCDC_TPDS_2026.pdf)
- **Peer-reviewed PVLDB 18(9):2859–2871, 2025:** *Locality-Aware Cache Replacement Policy for Graph Traversals* combines graph-aware serialized layout with replacement policy. Its Neo4j integration improved latency up to 1.23x. This motivates a Skyframe demand-trace layout experiment; it is not evidence that Neo4j ordering or its speedup transfers to Skycache. [LAC paper](https://www.vldb.org/pvldb/vol18/p2859-korkmaz.pdf)
- **Current normative API documentation, observed 26 October 2026:** REAPI supports capability-bounded batches, FindMissingBlobs, negotiated compression, and whole-blob digest verification. Compressed ByteStream reads require zero read_limit. Main now describes SplitBlob/SpliceBlob as v2.12 interfaces replaced by streaming GetChunkMapping/RegisterChunkMapping in v2.13; optional support requires capability checks. This must be reconciled with the vendored proto and deployed server, not assumed present. [Official REAPI](https://raw.githubusercontent.com/bazelbuild/remote-apis/main/build/bazel/remote/execution/v2/remote_execution.proto)
- **Foundational, peer-reviewed ATC June 2016:** FastCDC reduces bytewise chunk-boundary CPU costs; CDC addresses fixed-boundary shifts after edits. It remains a useful simple baseline despite newer work. [FastCDC](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia)

### Inferences

**P1/P2 trace-driven experiment ladder:**

- Measure distinct demanded record bytes, block-aligned authenticated bytes, unique fetched chunk bytes, re-read/hash bytes, compressed wire bytes, RPC count, and version-to-version reused bytes separately.
- Replay existing demand traces over (a) current layout/1MiB; (b) 512/256/128KiB where bundle limits permit; (c) record-aligned bounded packing by deterministic key/function/observed co-access; (d) FastCDC and a newer hashless CDC comparator at **equal observed mean chunk size and reported variance**. Do not reward an algorithm merely for emitting smaller chunks.
- A 64KiB sweep can easily exceed the 1MiB bundle cap even before reaching 32,768 references. At 4GiB logical closure, 128KiB means 32,768 references before protobuf overhead; the bundle-size bound may bind first. Measure actual encoded envelope size and reject invalid variants. Manifest sharding belongs to a separate future protocol/version decision.
- CDC helps only if serialized bytes remain stable after small source/graph changes. Measure canonical ordering, UUID/offset/timestamp churn and pack compaction first. Stable record-addressed blocks or shallow structural deltas may beat byte-level CDC with much less CPU. Parent closure must remain bounded, with explicit checkpoint/flattening rules; current publication-specific logical-key mapping cannot be replaced by an assumed key-equals-digest identity.
- Avoid unauthenticated partial ByteStream reads as a shortcut: a range cannot be checked against a whole-blob SHA-256 digest alone. Smaller CAS chunks preserve existing authentication. A persistent Merkle block-proof design could authenticate small ranges from a trusted root but adds proof/index/version machinery and should be deferred unless cold initial authentication remains dominant.
- Compression should be optional and negotiated: for uncompressed U, compression ratio alpha, bandwidth B, compression/decompression rates v_c/v_d, an approximate serial break-even is `(1-alpha)U/B > U/v_c + U/v_d`. Apply measured overlap and latency afterwards. Compression may win on WAN and lose on warm LAN or CPU-bound consumers.
- Let x be useful demand per chunk and c its total bytes. The relevant ratio is distinct fetched bytes / distinct useful bytes, not nominal hit rate. Smaller c can reduce amplification but raises metadata, RPC, and per-object hashing costs. For random independent per-record demand probability q across k equal records/chunk, the expected fraction of chunks fetched is `1-(1-q)^k`; correlated graph demand invalidates that simple independence model and should be replayed directly.
- FindMissing break-even: added lookup latency/CPU must be below avoided upload fixed costs plus bytes/B. A tiny one-off publication may favor direct batched upload; a repeated large closure should favor missing-only upload. Use already known parent references before a redundant server existence scan, while honoring retention semantics.

**Proposed gates:** cold transfer/layout candidate reduces distinct fetched bytes at least 25% and target cold wall time at least 10%, stays within v1 envelope and current memory budgets, and meets the protected-arm 3% regression ceiling. These thresholds are proposal gates, not speedup predictions. Keep the simplest valid candidate when performance intervals overlap.

### Gaps

- No current trace establishes how much publication churn is due to shifted boundaries versus changed records, compression entropy, or unstable serialization.
- No evidence yet demonstrates demand-layout optimality; clustering can improve locality while harming cross-version deduplication.
- Deployed capabilities, max batch sizes, compression, server CAS retention costs, and actual mapping-RPC availability remain unmeasured.
- The latest CDC preprint's claim of ICDE 2027 acceptance is author-reported; its results need reproduction on Skycache data, and the arXiv 2024 predecessor is not independent corroboration.

## 3. How should concurrency, admission, prefetch and tail behavior be planned?

### Takeaway

Use bounded, demand-prioritized scheduling and measure queueing before adding more concurrency. Upgrade cache admission or prefetch only from actual multi-build traces; preserve the current coalescing and cumulative budgets.

### Cited Findings

- **Peer-reviewed NSDI, April 2024:** PReQuaL selects among servers using estimated latency and requests in flight, with asynchronous reusable probes, rather than balancing CPU utilization alone. Its distributed replica-selection setting differs from this single Skycache endpoint, but supports measuring queue age/latency instead of “more workers” as an objective. [PReQuaL](https://www.usenix.org/conference/nsdi24/presentation/wydrowski)
- **Peer-reviewed NSDI, April 2025:** Google's storage QoS deployment report finds that lower priority does not mechanically imply worse latency when high-priority bands are overloaded. Scheduling classes must be validated under contention. [QoS alignment paper](https://www.usenix.org/conference/nsdi25/presentation/buckley)
- **Peer-reviewed SOSP, October 2023:** S3-FIFO uses a small probationary FIFO to remove one-hit objects quickly before admission to the main cache, providing a simple non-ML baseline for scan-heavy, multi-build retained storage. Its evidence comes from 6594 traces, not Skycache. [S3-FIFO](https://pdl.cmu.edu/PDL-FTP/Storage/FIFOqueues-SOSP23_abs.shtml)
- **Peer-reviewed workshop, HotStorage July 2025:** PaperCache supports runtime policy switching and periodically chooses low-miss-ratio policies; the authors report improvements in their workloads. Treat it as evidence that workload phases matter, not an instruction to add adaptive machinery before static baselines. [PaperCache author record](https://www.michaelstumm.com/Shakiba-HotStorage25.html)
- **Accepted OSDI 2026; arXiv 28 August 2026:** Learning-Augmented Heuristics/S4-FIFO separates infrequent cache-level parameter learning from the request path; its evaluation uses 4140 training and 1035 evaluation traces. No evidence here warrants ML in Skycache now. A useful design principle is keeping any later control-plane adaptation outside per-read work. [OSDI program record](https://www.usenix.org/conference/osdi26/presentation/xia); [paper](https://arxiv.org/abs/2608.27975)
- Official gRPC docs recommend bounded retries, exponential backoff, retry throttling and server pushback. Hedging can lower tails but duplicates load; gRPC supports delayed attempts, cancellation and throttling. These are design constraints, not evidence that hedging benefits the current single-backend Skycache. [Retries](https://grpc.io/docs/guides/retry/); [Hedging](https://grpc.io/docs/guides/request-hedging/)

### Inferences

**P2 scheduling design to test later:**

1. Keep distinct caps for network download, local read/hash, and publication, plus an explicit byte-in-flight bound. Sweep concurrency across a small range such as 1/4/8/16/32 using realistic budgets. Record queue age, p50/p95/p99 RPC latency, blocked evaluator time, CPU, disk queue and fallback rate. Little's identity `L=lambda·W` is bookkeeping for a stable flow, not a rule that concurrency should grow without limit; a starting WAN estimate is bytes in flight around bandwidth-delay product, then validate.
2. Existing striped singleflight is a sound bounded baseline. A bounded digest-to-future table is justified only if measured unrelated-digest stripe collisions delay useful work. Preserve cancellation, error fanout, lock ordering and state cleanup.
3. Prioritize data that unblocks active evaluation ahead of speculative prefetch and background publication. Use age-based fairness so low-priority work still completes. Score prefetch by `p(use-before-eviction)·critical-path-stall-avoided - transfer/hash cost - eviction externality`. p can initially be an empirical counter; there is no need for ML.
4. Coalesce small demanded metadata into capability-compliant BatchRead requests with a strict maximum batching delay. Large batches can head-of-line block urgent small data; prioritize based on measured wait and predicted service time.
5. Simulate retained-cache LRU, SIEVE and S3-FIFO from several revisions/build types at fixed **byte** budgets. Evaluate miss cost weighted by bytes, verified-read CPU and critical-path stall, not object hit ratio alone. A simple admission benefit density is `expected future stall saved / retained bytes`; include one-hit publication scans and independent authentication-metadata capacity. Start with static policies.
6. Retry only transient idempotent reads/uploads under the same total byte/RPC-time budget. Respect server pushback; never retry invalid digest/protocol errors. Avoid hedging unless a real replicated backend and measured tail problem exist; choose delayed idempotent reads with an extra-byte ceiling if later tested. Do not hedge catalog commits merely to improve a latency chart.

**Measurement matrix and controls:** separate retained-cache cold/warm, OS page-cache cold/warm, server CAS cold/warm, fresh/warm Bazel daemon, and LAN/WAN RTT/bandwidth conditions. Keep source commit, binary hash, namespace, target set, output policy (minimal/toplevel), publication candidates, remote action/output-cache state, budgets, machine CPU/memory, and background contention fixed. “Cold” alone is insufficient.

Run balanced randomized paired blocks after a declared warm-up; freeze the replay corpus so repeated publication/discovery does not silently improve later arms. Report individual runs and paired effect intervals. Start with approximately 10 paired runs per main arm and expand only if intervals do not decide a predeclared practical threshold. Use enough RPC observations for tail estimates and enough independent builds for build-level tails; n=3 build medians do not establish p99.

**Go/no-go ordering:** P0 attribution/default realism → P1 warm access/publication candidates → P1/P2 cold chunk/layout/compression → P2 concurrency/admission → speculative structural proof/delta format or learned policy. Stop after the narrow change that meets the target; do not accumulate unvalidated optimizations.

### Gaps

- No WAN, overload, replica, multi-tenant, or realistic eviction-pressure measurements were supplied.
- Full-workload benchmark overrides obscure whether defaults already cause budget misses.
- Prefetch utility depends on future use before eviction; current access statistics do not establish this.
- Publication durability makes “asynchronous publish after exit” a semantic change, not merely an implementation optimization; this research recommends measuring batching/overlap within existing completion guarantees first.
