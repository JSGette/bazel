# Bonanza contracts relevant to shared evaluation

Read-only source audit, 2026-11-07. Bonanza revision: [`bf9368403b95540ad07e0fd33faf5210b9d8b86b`](https://github.com/buildbarn/bonanza/commit/bf9368403b95540ad07e0fd33faf5210b9d8b86b), resolved using `git ls-remote`, then inspected through the GitHub connector. This is source evidence, not a Bonanza deployment benchmark or a milestone verdict.

Compared with our [gated plan](../../plans/shared-evaluation-gates-2026-11-07.md) and [M1 probe design](m1-probe-design.md). The relevant distinction is immutable stored results versus active evaluation state: Bonanza implements the former across requests; the inspected executor creates the latter afresh for each evaluation action.

## Verified contracts and their limits

1. **Storage identity is independent of a checkout directory.** Object Store addresses immutable objects by references containing a SHA-256 digest and structural metadata; outgoing object references make a DAG. Filesystem messages carry file contents, executable bits, directory entries and symlink targets. Small directories may be inlined, and large files use content-defined chunks. The schema represents executable status, not arbitrary POSIX metadata. Identical subtrees can therefore retain identity across different roots; a root hash alone does not identify every computation's actual inputs. [Object protocol][objects], [filesystem schema][filesystem], [Merkle-tree design][merkle].

2. **A build sends explicit inputs plus a logical request.** The client scans local modules into Merkle trees, places module names/root references and build policy in `BuildSpecification.Value`, and supplies it as an override for the singleton `BuildSpecification.Key`. Requested keys separately describe the build query and configurations. Module roots reject symlinks that may escape them. This is close to `Evaluate(snapshot, query)`, without embedding the full snapshot into every logical key. [Client construction][client], [build specification and query schema][analysis].

3. **Immutable uploaded data does not by itself establish coherent capture.** The client traverses live directories and reads files; the later upload walker checks reconstructed file/chunk references against captured references. That catches a changed payload when uploading it. The inspected paths do not establish an atomic multi-file capture or our stronger detect-and-retry guarantee. Retain M2's mutation-during-capture tests; do not count CAS identity as passing them. [Client scan][client], [upload validation][capture].

4. **Evaluation remains explicitly Skyframe-like.** Keys are protobuf messages; values may be protobufs or native Go values. `Environment` records requested dependencies, and a missing dependency causes the computation to restart later. `Evaluation` stores the message value plus direct *variable* dependencies: those transitively affected by supplied overrides. `Graphlet` packages an evaluation with selected dependency evaluations, with inline/external representations and B-tree indexing. This is not an assumption that all native values are persistable. [Computer interface][computer], [environment][environment], [evaluation protocol][evaluation].

5. **Cache lookup validates observed dependency values, with two reuse granularities.** The cache namespace incorporates signing identity, reference format, encoders and the set of overridden keys; lookup identity adds the logical key and subsequently hashes dependency key/value records. A lookup may return expected dependencies, more dependencies for a changed dependency shape, a graphlet hit, or a single-value hit. Native values contribute a dependency hash instead of serialized native state. The implementation tries graphlet reuse first and can fall back to value reuse; graphlet grouping hoists selected dependencies to limit growth/churn. [Cache protocol][cache], [lookup and graphlet construction][recursive].

6. **Persistent reuse is wired; a shared live graph is not demonstrated.** The executor constructs a new `RecursiveComputer` with an initially empty key-state map for each evaluation action, backed by storage-resolved signed cache tags. It uploads results and flushes tags before returning. Thus different builds can reuse completed results without requiring one long-lived evaluator graph. This source path does not establish cross-invocation sharing of pending computations. Tag resolution reports whether the referenced DAG is complete, and tag updates carry a lease; these are concrete publication/liveness contracts worth borrowing for M5. [Executor][executor], [per-request state][recursive], [tag protocol][tags].

7. **Remote placement and phase barriers are separate questions.** A build itself is scheduled to `bonanza_builder`; action and repository execution are remote requests from the evaluator. Builder queues distinguish local computations from remote calls, with separate concurrency limits. `BuildResult` requests each target's completion; completion requests file roots, which can request action results. Repository evaluation also consumes action outputs as dependencies. **Inference from these paths:** there is no graph-wide analysis-then-execution barrier in this orchestration. This does not establish arbitrary execution-dependent rule analysis or removal of all ordering constraints: dependency edges and rule APIs still constrain evaluation. [Builder wiring][builder], [build orchestration][base], [completion][completion], [file roots][file-root], [repository execution][repo], [remote execution protocol][remote].

8. **Output identity is already separate from local presentation, but client materialization is unfinished evidence.** Action results carry output-directory objects; the inspected `build` CLI ends by reporting an outcomes reference/link rather than creating a local `bazel-out` tree. The author's October slides depict a `bazel-out` VFS mount; that picture is not proof of implemented CLI materialization at this revision. Keep an output view as a separately owned adapter in our design. [Action result][action-result], [CLI completion][client], [October slides, pp. 6–10][slides].

9. **Do not assume a demonstrated worktree capacity.** No quantified concurrent-worktree limit, throughput curve or memory-per-variant measurement was found in the inspected README, repository docs or October slide deck. The slides describe frequent branch changes and full result graphs as goals. Configurable evaluator/worker concurrency is not a measured count of simultaneous worktrees. The README still describes build-result caching as unavailable, while the pinned executor now wires a cache: record that documentation/source discrepancy rather than treating either as a measured performance result. [README][readme], [builder configuration][builder-config], [October slides, pp. 26–28][slides].

## Five experiments to carry into our gates

These are our proposals, not claims about Bonanza's measured behavior.

| Experiment | Concrete contract or falsifying test |
| --- | --- |
| **M1: compare private hosting, value sharing and graphlet sharing separately.** Keep the current same-binary native/private comparator first. Extend replay to charge graphlet decoding, bytes transferred, dependency validation, lookup round trips and retained candidate/index state. | Report supported typed overlap and an optimistic ceiling separately. Model branch A→B→A and disjoint edits. A graphlet saving round trips may increase invalidation or retained bytes; neither a cache hit nor serialized bytes proves CPU/RAM savings. |
| **M2: separate immutable snapshot roots from dependency observations.** Use the root to bind a request; record typed file, directory-membership, missing-path and configuration/repository observations. Candidate identity includes a semantic format/evaluator epoch. | Relocate identical checkouts and require reuse; change same-size bytes, executable bit, symlink destination, directory membership, missing→present, repository binding and environment independently and require the relevant observation to change. A whole-root hash in every key would reject unrelated-edit reuse. |
| **M2: make snapshot capture an explicit transaction.** Begin with a supported coherent capture mechanism or bounded validate-and-retry; reject unsupported ambient reads. CAS publication follows successful capture. | Mutate two related files and rename directories while capturing; accept one coherent version or an explicit retry/fallback, never a mixed accepted snapshot. Verify negative-path observations against captured directory state, not the later live filesystem. |
| **M3/M5: make cached variants immutable and candidate indexes replaceable.** Prototype separate graphlet/value records with bounded dependency-refinement lookup, explicit missing-object handling and publish-after-durability ordering. Defer live pending-work sharing to M4. | A→B→A must recover A; conditional dependencies must not admit a stale hit. Remove a referenced object, interrupt publication and restart: require recomputation/fallback, not partial success. Count lookup depth and retained variants; apply the actual GC/lease failure suite in M5. |
| **M2/M3: demote output base to an output-view adapter.** Evaluation consumes snapshots and yields immutable result references; invocation diagnostics, cancellation and materialization ownership remain separate. Keep phase changes as the plan's later experiment. | Delete/recreate or relocate one view without invalidating reusable evaluation; materialize two variants concurrently and compare both outputs with isolated oracles. A later phase experiment should time execution of one ready target while another target is still analyzing, with explicit dependency and failure semantics. |
