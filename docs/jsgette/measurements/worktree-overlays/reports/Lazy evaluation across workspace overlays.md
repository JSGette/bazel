# Lazy evaluation across workspace overlays

**Give each build a stable source view and let it share work at the level of an individual operation.** A build can pin its overlay at submission, start at its requested target, and pull more dependencies as capacity becomes available. Two builds can join one eligible operation as soon as they establish that it will produce the same result for both. To serve a later caller after that operation leaves memory, the system needs a way to find its completed result. Three experiments exercised these distinctions. They favor a Git-aware source reader and a bounded discovery experiment. They give little reason yet to commit repository-wide graph metadata or replace Skyframe. [Problem statement](../PROBLEM.md)

## Eight different views shared one library operation

A Git commit identifies where editing started. A draft name such as A identifies a workspace that can change. A build needs a third identity, the **effective source revision** it agreed to read. A sparse map of edits is economical when a producer knows exactly which paths it added, replaced or deleted. Reads can consult that map and fall through to the base tree. Directory reads also need rules for merging children and hiding deleted descendants. A persistent tree turns the resulting namespace into an immutable root, sharing unchanged child trees and blobs. The two models fit together. A cooperating editor can publish a batch of replacements as a new root while an existing build holds the old one. A live directory remains a convenient editing surface, but scanning it while arbitrary writers run can capture files from different instants. Atomic publication of the *result* cannot correct a mixed capture. [Git trees and draft models](<../research_notes/Git bases and workspace overlays/view_models.md>) · [Git objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)

The first experiment used alternate Git indexes in a temporary repository. Eight callers pinned eight different trees over commit `12896084b565`. A1 contained unstaged bytes that differed from the real index. B1 removed `old.h` and added `new.h`. While A1's request was registered, the experiment published A2. Reading the original A1 still yielded its original application text, B1 yielded the base text, and all revisions referenced the same `lib/` tree. HEAD and the staged index were preserved. This tests known edit batches and on-demand reads. The cost of discovering edits in a large live checkout remains open. [Overlay probe](../experiments/overlay_probe.py) · [Recorded observations](../experiments/overlay_results.json)

In each batch, **eight real caller threads** observed their own inputs and met at a barrier. All eight library requests resolved the same path to the same blob under the same transform version and declared context. One producer uppercased the bytes and seven callers joined. The header-name operation formed two groups from the names each directory actually contained. Two producers and six joiners delivered four `old.h` and four `new.h` answers. A key using only commit and target returned the wrong header for B1. A key using the full view root would have created eight entries for the library. With other inputs controlled, the full root is a safe, conservative source key. A more precise operation key permits sharing across roots. The barrier establishes overlap under controlled arrivals. These were fixture transformations, so the counts say nothing about native compiler throughput. [Windows results](../experiments/overlay_results.json) · [Ubuntu WSL results](../experiments/overlay_results_linux.json)

The distinction matters during analysis. A function selecting a BUILD file can observe the *absence* of a higher-priority file. A glob can observe a new directory member even when all previously read files have identical bytes. For dynamic dependencies, discover them separately in each view or validate a prior result's recorded observations against the requesting view, including configuration, external inputs and toolchain where relevant. Once analysis has produced an eligible action, its command and actual input root can agree across otherwise different views. Each caller still needs its own output delivery and diagnostics. [Bazel package lookup](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/skyframe/PackageLookupFunction.java#L149-L185) · [BuildXL observed inputs](https://github.com/microsoft/BuildXL/blob/main/Documentation/Wiki/Advanced-Features/Two-Phase-Cache-Lookup.md) · [REAPI action identity](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto#L636-L698)

## Discovery must fit the window too

The second experiment interleaved eight logical requests in **one thread**. Each requested 4,096 leaves from a generated namespace of a billion possible names. Only demanded names were generated. The first 4,095 inputs were common and the final input differed by request. The scheduler admitted at most four outstanding dependency subscriptions per wave. Expanding every dependency before admission created a peak of **32,768 queued or subscribed descriptors**. A resumable cursor that pulled the next dependency on admission reduced that peak to **four**. Both versions also held eight root accumulators and transient state for active work. These are logical record counts for a streamable dependency sequence. They measure neither JVM memory nor physical execution parallelism. [Window probe](../experiments/window_probe.py) · [Recorded counters](../experiments/window_results.json)

A window needs somewhere to put unfinished work. With one active item, a 4,096-deep chain parked 4,096 parent frames. A separate fixture delivered one result to 4,096 waiters, each with a distinct recipient token. Both fixtures could move their parked records into SQLite and recover the same answers. A bounded evaluator would need to release execution slots while parents wait, keep a path for children to run, and budget the bytes of queues, saved continuations, subscribers and results. A dependency generator that creates its whole list internally can exhaust memory before a downstream cursor ever sees it. [Chain and waiter observations](<../research_notes/Lazy evaluation across workspace overlays/window.md>)

With the same four-subscription window, retention changed the amount of work. The first eight requests contained **4,103 distinct operation inputs**. An in-flight table alone executed 8,198 operations because later waves missed completed producers. A SQLite result table executed 4,103 and incurred 20,483 lookups. When a later request repeated the first root, the in-flight-only arm executed all 4,096 leaves again. The reopened database served all 4,096 through lookups with zero executions. Increasing the window to 16 let all eight callers join common operations during the initial phase, but the late caller still needed retained results. [Window results](../experiments/window_results.json)

For healthy concurrent callers, a candidate protocol is to look up a completed result, atomically join or claim an active producer on a miss, and recheck completion after acquiring ownership. Publish retrievable output data before recording success. A missing blob makes its receipt unusable. Cancellation should detach only the departing subscriber's interest. An interrupted producer can leave work eligible for retry, particularly if it finished an external action before publishing its result. The probes establish coalescing for pure operations with known keys. They do not establish crash-proof exactly-once execution. [Branch cache coordination](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/RemoteSpawnCache.java#L100-L175) · [REAPI retention rules](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto#L143-L164)

## A Git reader and a committed index buy different things

The third experiment reconstructed only the packages reachable from one target. Every arm used the same reader to consult a sparse overlay first, then look up base paths and blobs in Git. The optional index added a separate fact per package, recording the generator and schema, definition blob, observed presence or absence of a file, and resulting dependencies. Generating it parsed 64 packages and committed **64 shards totaling 9,772 bytes**. The clean target reached four packages. Plain discovery parsed four definitions totaling **48 bytes in five Git path lookups**. Validating the hints avoided all four definition parses but read **four shards totaling 612 bytes in nine lookups**. Counts concern payload returned and explicit path lookups. They exclude Git's internal I/O and do not establish a timing advantage. [Index probe](../experiments/index_probe.py) · [Raw counts](../experiments/index_results.json)

Changing one definition redirected a dependency. Adding a previously absent flag enabled a fifth package without changing the referring definition's bytes. Blind reuse returned a wrong graph in both cases. Checking the recorded inputs caught each change and reparsed just one package. Missing, malformed and incompatible shards also fell back to parsing. This assumes a trusted generator whose observations cover everything the result depends on. A Git driver can answer path questions without any checked-in hints. Local, demand-built hints can avoid repeated parsing without repository churn. Committed hints can seed a cold checkout, at the cost of generation, validation, transfer and maintenance. The small definitions here made fresh discovery cheap. The experiment supports retaining all three comparison arms before choosing to commit metadata. [Index findings](<../research_notes/Lazy evaluation across workspace overlays/index.md>)

## A package and glob experiment outside Skyframe

Linux, macOS and Windows can expose ordinary private directories materialized from a pinned logical tree. A virtual filesystem such as EdenFS offers lazy projection as a separate option. Define the bytes and names the consumer observes. Git filters or CRLF conversion can change checkout bytes. Case collisions, symlink representation and executable mode can change which trees a volume can faithfully present. The probes used controlled regular files. Native Windows and Ubuntu under WSL agreed on their substantive results. macOS remains an unexecuted design target. Cross-host binary reuse would require compatible action inputs and execution context. [Git attributes](https://git-scm.com/docs/gitattributes) · [Projection study](<../research_notes/Git bases and workspace overlays/projections.md>)

The pinned Bazel branch already runs private evaluators concurrently and coordinates eligible action results. Skyframe already supports asking for prerequisites dynamically and restarting when answers become available. A follow-up MVP checked **one package lookup plus one glob** against Bazel on eight overlays. Every cursor resumed correctly after process exit. Repeatedly seeking to saved directory positions introduced measurable rediscovery, which gives the benchmark a concrete cost to investigate. [Experiment results and reproduction](<Resuming a Bazel package glob.md>) · [Branch scope](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/docs/jsgette/plans/multi-worktree-completion-roadmap.md#L14-L69) · [SkyFunction contract](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/skyframe/SkyFunction.java#L36-L55)

If that slice survives, benchmark representative concurrent Bazel builds against private evaluators and independent servers with equivalent caches and total resources. Measure elapsed time until all builds finish, per-request latency and peak process-tree memory. Investigate a versioned or replacement evaluator if repeated discovery or evaluator-owned graph state dominates those costs and a competing slice can return identical answers with a material improvement. That benchmark should determine which implementation deserves polish.
