# Demand-driven evaluation and duplicate suppression

## What does a sliding window actually bound?

### Takeaway

Bound the number and size of runnable operations separately from the records that describe unfinished work. If N build requests share W execution slots, the system still needs to remember which of those requests are interested in each result. A bound on W alone says little about graph or subscriber memory.

### Cited findings

- Skyframe already discovers dependencies on demand. A SkyFunction may request a value during execution, return when it is missing, and restart when the dependency becomes available. Its interface explicitly distinguishes independent dependencies that can be requested together from later requests whose identities depend on earlier answers. Optional per-key computation state can be dropped under memory pressure. [Pinned SkyFunction contract](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/skyframe/SkyFunction.java#L36-L55) · [Dependency groups](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/skyframe/SkyFunction.java#L249-L299) · [Droppable computation state](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/skyframe/SkyFunction.java#L505-L529)
- The branch evaluator selects an in-memory graph, including an edgeless option. Bazel documents distinct tradeoffs for discarding analysis data before execution, omitting incremental graph edges, and discarding state after a build. Discarding state afterwards alone leaves the current build's high-water mark unaffected. [Pinned evaluator](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/skyframe/InMemoryMemoizingEvaluator.java#L59-L89) · [Bazel memory options](https://bazel.build/advanced/performance/memory)
- Dask limits the number of runnable root tasks sent to workers and queues excess roots at the scheduler. Its scheduler maintains a dictionary of task records until it can forget them. This is a concrete example of how limiting worker queues can move some memory to the scheduler. Dask's term *root task* refers to producer-side tasks, whereas a Bazel user requests a target on the consumer side. [Dask scheduler states](https://distributed.dask.org/en/latest/scheduling-state.html#task-state)
- In *Build Systems à la Carte*, the model of Shake suspends work as dynamic prerequisites are requested, keeps a set of completed keys during evaluation, and uses persistent traces recording dependencies for subsequent builds. The paper distinguishes choices about scheduling from choices about reuse. [Mokhov, Mitchell and Peyton Jones, §5.3](https://simon.peytonjones.org/assets/pdfs/build-systems-original.pdf#page=21)
- Temporal demonstrates one alternative to serializing arbitrary live stack frames. A worker caches a workflow's current state and can reconstruct its progress from recorded event history when necessary. Replaying such history consumes work. The analogy concerns continuation representation, not the identity of two build actions. [Temporal workflow state and replay](https://docs.temporal.io/sticky-execution)

### Inferences

- Consider a chain of depth D and a global window of W slots. If W suspended parents keep their slots while waiting for a child, the next child cannot enter. A proposed evaluator would release the slot on suspension, store enough state to resume or replay, and ensure dependencies of parked parents can still be admitted. A cycle requires an error or existing cycle-handling semantics, independently of scheduling fairness.
- At a node with F prerequisites, enumerating the full list and then starting W children retains F descriptors. One option is a restartable cursor over stable ordered inputs, expanding a page at a time and spilling progress and partial results. A prerequisite generator that materializes F elements internally defeats that bound. A function that must examine F results simultaneously requires a streamable representation, paged data, or an explicit exemption.
- Separate budgets for active operation count, retained bytes, ready pages, and parked requests. N admitted roots can exceed W by orders of magnitude. Spilling request rows to disk and choosing ready work in round-robin order across roots is one candidate. Joins on dependent operations must inherit some service from their subscribers. A single slow client should not keep every other client's completed result in RAM. Independent outputs require separate publication or materialization per requesting view.
- Size the research test by changing *four variables independently* — total possible graph size, demanded width/depth, N, and W. Count requested observations, evaluator restarts, ready records, suspended parents, subscriber records, live result bytes and persistent rows/bytes. With a fixed requested slice and growing unrelated repository, unnecessary discovery should remain flat. A broad genuinely demanded closure is allowed to cost more.

### Gaps

- These sources do not establish that arbitrary Bazel SkyValues, dependency continuations, or diagnostics have a portable, compact representation. A bounded count of small test records is weaker than a byte bound and neither implies a fixed process RSS.

## How does a later request avoid doing the same work again?

### Takeaway

There are two time intervals. Overlapping callers can rendezvous on a known operation identity. A later caller needs a discoverable record of successful completion and access to the associated result.

### Cited findings

- Go's singleflight group lets overlapping callers with an equal key wait for the same function invocation. Its guarantee concerns the operation in progress. [Go singleflight contract](https://pkg.go.dev/golang.org/x/sync/singleflight#Group.Do)
- At the pinned Bazel head, the cross-workspace path is restricted to participating spawns with applicable read and write cache policies, including whether the request busts caches. The constructor requires synchronous disk caching. It keys a lease by cache path, digest algorithm, and the REAPI action digest including its size. Spawns outside this path use normal cache handling. [Eligibility and key](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/RemoteSpawnCache.java#L71-L137) · [Read and write policies](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/RemoteExecutionService.java#L347-L378)
- The branch registry waits interruptibly when the same key is running or all 256 eligible leases are occupied. This count covers leases, including cache lookup and publication. It does not cap other execution, waiting threads, analysis keys or graph storage. Releasing a lease wakes contenders. An interrupted waiter can leave independently. [Registry and limit](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/SharedActionExecutionRegistry.java#L20-L73)
- The branch performs cache lookup under the lease. A follower rechecks the cache after admission and materializes outputs into its own execution context. Only successful zero-exit local results pass the upload gate. On failure or cancellation an unpublished result can therefore be retried. This mechanism serializes eligible lookups as well as suppressing successful duplicate work. [Lease release and lookup](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/RemoteSpawnCache.java#L134-L175) · [Required outputs and download](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/RemoteSpawnCache.java#L230-L249) · [Successful publication eligibility](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/RemoteExecutionService.java#L1645-L1657)
- REAPI gives repeatable actions an identity that includes a command and input root. It specifies cache-result lookup separately from content storage, permits result eviction, and allows an executor to run the action more than once. An action carrying `do_not_cache` cannot have its in-flight requests merged. [Action definition](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto#L636-L698) · [Cache retention and referenced blobs](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto#L143-L164) · [Execution semantics](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto#L110-L114)
- SQLite's documented recursive query example can release each consumed row while streaming. Requiring exact suppression of previously seen rows using `UNION` also requires retaining information about those rows, even after the execution queue stops holding them. [SQLite recursive query examples](https://www.sqlite.org/lang_with.html#recursive_query_examples)

### Inferences

- For arbitrary out-of-order revisits of n distinct completed keys from a universe of U possible keys, an exact membership test must distinguish all possible completed subsets of that size. That takes at least log₂(binomial(U,n)) bits *somewhere* in the general case. A result store addressed by the operation key can itself serve as the index. An additional ledger is not inherently necessary. Special traversal orders can compact history. The argument does not require retaining the full dependency graph or keeping any particular index in RAM.
- A fast path can read a completed result, then atomically join-or-create an in-flight entry after a miss. A new owner must recheck completion if another owner could have published between that miss and acquisition. Publish usable output blobs before the success record, then release interest and wake waiters. A receipt pointing to evicted bytes is a miss unless another valid source can supply those bytes.
- Measure new executions per eligible semantic identity, simultaneous producers per identity, requests served by active work, later result hits, retries, and materializations. Several consumers of one successful result still incur separate lookups and local delivery. A hot key with N consumers may require N registrations, independent of its single execution.
- An early exit by one subscriber should detach its interest. If others need the result, candidate policies include a producer owned by the shared operation or allowing a surviving request to retry after the original owner cancels. These policies have different actual execution counts. A crash after a subprocess finishes but before its success record becomes durable leaves ambiguous history. Choose an explicit failure policy for replayable operations. Actions with side effects need separate eligibility rules.

### Gaps

- A retained action descriptor does not prove that a process observed only its declared inputs, or that a CAS will retain the result indefinitely. No general exactly-once guarantee follows from an in-flight table plus an evictable cache.

## Where should cross-overlay identity meet Skyframe?

### Takeaway

Use a pinned view to make discovery coherent. Join across views once the operation's full semantic inputs are available, or reuse a completed candidate after validating the observations that determined it.

### Cited findings

- BuildXL indexes past executions by a weak fingerprint, obtains candidate observed pathsets, and combines each pathset with current observations for a strong lookup. File reads, probes and directory enumerations can all matter. Its documentation discusses many pathsets for one weak key as a lookup cost. [BuildXL two-phase lookup](https://github.com/microsoft/BuildXL/blob/main/Documentation/Wiki/Advanced-Features/Two-Phase-Cache-Lookup.md)
- Skyframe's contract requires dependency requests on values that influence results. The pinned evaluator already implements dynamic discovery and isolated in-memory graph storage. These facts let the research distinguish reuse outside the evaluator from replacement of evaluator-managed state. [Skyframe model](https://bazel.build/reference/skyframe) · [Pinned in-memory evaluator](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/skyframe/InMemoryMemoizingEvaluator.java#L24-L35)

### Inferences

- A view root identifies the effective source tree under a defined projection. It excludes configuration and toolchain unless those are explicitly included in a separate semantic key. Querying a label in a pinned view and configuration is a safe starting namespace when other relevant inputs are controlled. A common base commit and label do not justify a shared in-flight analysis when one view may introduce a previously missing header.
- Once a query resolves to a fully specified eligible operation, N distinct views with identical semantic inputs can share one producer. For pure functions with dynamic reads, a previous completed trace offers a finer comparison. Check negative path observations, directory membership and relevant external state against the current view. Count validations per saved execution. Conservatively perform discovery separately whenever equivalence is unknown.
- Keep the view provider and completed action reuse outside Skyframe as the first comparative baseline. Try query replay or spilling for one deliberately selected pure function only if measured live evaluator state or repeated discovery dominates. Consider a new evaluator when a representative dependency closure exceeds the memory budget under existing facilities, the dominant data is evaluator-owned, and a narrow competing evaluator demonstrates matching outputs with better end-to-end cost. A toy window establishes a mechanism worth testing, not a performance result for Bazel.

### Gaps

- Which Bazel functions can expose dependencies incrementally, stream their outputs, or afford replay remains unmeasured. Disk I/O, GC/pinning, dense dependency validation and platform-specific output materialization can outweigh saved work. The next measurement should attribute those costs separately from action execution.

### A Git-aware driver or a checked-in structural index

**Source observations.** Git distinguishes comparisons of the working tree with the index, the index with a commit, and the working tree with a commit. Plain `git diff` omits staged-only changes, and tracked diffs do not enumerate unrelated untracked files. `git status` distinguishes staged, unstaged and nonignored untracked paths. For an arbitrary checkout, these are leads for capturing actual build-visible file contents and directory entries. They do not freeze concurrent editor writes. Git ignore rules are a discovery policy. A build may still observe an ignored file unless the source view excludes it by construction. [Git diff](https://git-scm.com/docs/git-diff#_description) · [Git status](https://git-scm.com/docs/git-status#_description) · [Git ls-files](https://git-scm.com/docs/git-ls-files)

Git's own commit-graph can store changed-path Bloom filters for differences between a commit and its first parent. They accelerate path-history searches. A positive filter match is a candidate for an actual changed path. These filters provide neither an inventory of current dirty edits nor build dependency edges, configurations or reusable results. They are precedent for auxiliary indexes augmenting immutable history. [Git commit-graph changed paths](https://git-scm.com/docs/git-commit-graph#Documentation/git-commit-graph.txt---changed-paths) · [Git commit-graph file format](https://git-scm.com/docs/gitformat-commit-graph)

Bazel's package lookup tests candidate BUILD names by priority. Bazel's configured query uses analysis to select among conditional dependencies and incorporate build options. A Git tree can answer path and content questions. A package-directory or lexical-load index over that tree can accelerate selected structural questions, but the tree by itself does not determine which configured action will run. [Pinned package lookup](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/skyframe/PackageLookupFunction.java#L149-L185) · [Bazel configured query](https://bazel.build/query/cquery)

**Design choices inferred from these boundaries.**

1. An agent that owns edits could pass the base Git tree and a typed edit batch directly to a source driver. A build pins a published root. The driver answers demanded path, directory-membership and absence queries. A dispatcher can begin servicing N requests without loading N full repository models. A driver around existing worktrees needs an additional capture contract for untracked, ignored and concurrently edited files.
2. A generated *local* index can retain small independently loadable rows, keyed by a schema/generator version and the inputs each row actually summarizes. It avoids commit churn and can discard stale rows. The first checkout may still pay the generation cost. Measure generating the index only as queries arrive against building the entire index eagerly.
3. Shipping the same *derived* index in the repository can help cold machines, but now regeneration, merge frequency, transfer size and validation cost matter. Keep retrieved index shards separate from trusted semantic answers. Bind a shard to independent relevant input object IDs, a tree scope and the generator/schema. When edits affect those observations, fall back to fresh discovery. A checksum certifies bytes, not completeness or faithful extraction, so accepting the index as authoritative requires trusted generation/verification. A directory-membership witness detects a new subpackage or newly matched source that did not exist in the base. Validating only known file hashes misses additions.
4. A tracked summary stored inside a commit cannot straightforwardly declare the hash of that same commit, because the commit depends on its tree and the tree includes the summary. Key shards by source subtrees that exclude the summary, use a canonical input digest that explicitly excludes generated index paths, or store the summary out of band and key it by the finalized source root. If the checked-in representation instead becomes the *authoritative build language*, that is a larger change with new rules for generated targets and dynamic dependencies.

**Discriminating test.** On cold state, compare fresh demand-driven discovery, a local memo seeded on an earlier request, and a checked-in index shard under the same **effective** view. Exercise additions, deletions, higher-priority BUILD files, changed build configuration, and stale index format. Require identical results to fresh discovery, then count index bytes read, source entries touched, fallback discoveries and successful reused observations. An eagerly loaded repository-wide index can defeat the memory goal even if it saves parsing. A large full-tree validation scan can erase the expected cold-start benefit.
