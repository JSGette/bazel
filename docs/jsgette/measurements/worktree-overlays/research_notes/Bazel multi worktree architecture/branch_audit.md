# Branch implementation audit

## What does the branch actually implement?

### Takeaway
The native branch is a two-engine JVM host with private evaluators and output trees, eligible action-result sharing, and two narrowly immutable payload interners. It is a credible experimental foundation for a new ownership-oriented design, but it does not implement a common analysis graph, compiled Starlark reuse, churn-safe engine disposal, a daemon resource scheduler, or general Bazel feature parity.

### Cited Findings
- Audit pinned to `4f4b44b5a2c1780cdbb0215c4556de39d0f0a995`, branch `jsgette/native-multi-worktree-mvp`. The head adds the consolidated limitations/roadmap. Local Git confirms 16 commits since `9a2ababbd5cf113c31450fbe9214b501be8c58a2`; that base resolves in upstream `bazelbuild/bazel`. This is a comparison base for the branch, not a claim about today's upstream head. — [Branch head](https://github.com/JSGette/bazel/commit/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995), [upstream base](https://github.com/bazelbuild/bazel/commit/9a2ababbd5cf113c31450fbe9214b501be8c58a2)
- Local diff for `src` and `tools`: 59 files, 6,932 insertions, 186 deletions; numerous additional plan/measurement artifacts exist. The changes span launcher startup/ownership, Java server and runtime, action cache, metrics/global services, payload representation, tests, and a separate Python supervisor. — [Exact comparison](https://github.com/JSGette/bazel/compare/9a2ababbd5cf113c31450fbe9214b501be8c58a2...4f4b44b5a2c1780cdbb0215c4556de39d0f0a995)
- Native startup uses a new `shared_servers/v3/<name>/control` namespace and private `engines/<workspace hash>` output bases. Linux is enforced; batch, exec-server, explicit output base, and delete-output-on-shutdown are rejected. User-specified names are grouping/admission choices, not automatic Git-family discovery. — [Startup layout and restrictions](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/cpp/startup_options.cc#L798-L818)
- Startup compatibility preserves argument ordering and repetitions while excluding workspace/output paths and option provenance; the actual JVM launch environment is compared exactly through `/proc/<pid>/environ`, with values omitted from diagnostic output. `PWD` and `OLDPWD` are removed only from the JVM launch environment, while RPC client environment remains separate. — [Profile and environment comparison](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/cpp/blaze.cc#L1714-L1785), [PWD handling](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/cpp/blaze.cc#L758-L762)
- The first engine uses an ordinary `BlazeRuntime`; additional engines instantiate new module objects, replace workspace/output startup arguments, acquire native output ownership, pin physical directories, and create another `BlazeRuntime` and dispatcher. Services are reused deliberately; their global initialization is skipped for the extra engine, while each module's `globalInit` still runs. — [Native engine factory](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/runtime/BlazeRuntime.java#L1457-L1497), [service/module initialization](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/runtime/BlazeRuntime.java#L1623-L1639)
- Routing supports only `build`, `test`, `info`, `shutdown`; preemptible shared requests are rejected. The request supplies workspace/output identity and the daemon's first-engine registration ID; the server resolves the selected slot and acquires its current local registration. It is not yet a wire protocol where every request carries a recyclable selected-engine generation. — [Shared request validation/routing](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/CommandServer.java#L327-L378)
- Engine registry states are CREATING, READY, DRAINING, CLOSED; leases retain dispatchers, drain waits for lease count zero, and close removes registry ownership only after preconditions pass. Scoped shutdown waits for those leases and invokes engine cleanup before closing pinned directories/registration. — [Registry lifecycle](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/EngineRegistry.java#L48-L159), [engine shutdown](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/CommandServer.java#L398-L430)
- Graph-backed global interner pools are disabled before constructing shared runtimes; each graph still has its own `ConcurrentHashMap` of nodes. This is deliberate correctness isolation, with possible lost single-graph pooling efficiency to measure. — [disable before runtime creation](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/runtime/BlazeRuntime.java#L1038-L1045), [graph implementation](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/skyframe/InMemoryGraphImpl.java#L52-L105)
- Action reuse preserves the existing REAPI action digest and cache rules. The shared registry key includes disk-cache path, digest function, digest hash, and size. A lease covers lookup, execution, and publication; waiters retry lookup and materialize into their own execroots. The registry retains only immutable strings, with a 256-active-key bound. Uncacheable/read-disabled/write-disabled spawns bypass sharing. — [cache adapter](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/RemoteSpawnCache.java#L100-L176), [registry contract and bound](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/SharedActionExecutionRegistry.java#L20-L74)
- Cache-hit results require success and mandatory outputs. Publication uses the existing upload path, while shared invocation policy forces synchronous upload. Producer failure/cancellation releases the key; waiting consumers may execute again. This is not unconditional exactly-once execution and not a general shared computation scheduler. — [result validation](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/RemoteSpawnCache.java#L231-L248), [publication](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/RemoteSpawnCache.java#L338-L375), [synchronous policy](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/runtime/BlazeCommandDispatcher.java#L950-L984)
- Actual immutable sharing is limited to sorted directory-entry names/types and Starlark newline-offset arrays. Directory payloads contain no paths/owners; line-table wrapper retains filename and input size locally. Both use weak interners. Parsing/resolution still occurs separately and weak interning is not a byte-budgeted cache. — [directory payload interner](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/skyframe/CompactSortedDirents.java#L27-L62), [line-map representation](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/net/starlark/java/syntax/FileLocations.java#L26-L155)

### Inferences
- Retain the proven separation of physical outputs, local graphs, and immutable action digests. Treat Skyframe replacement as an independent analysis-store experiment, not a prerequisite for lifecycle repair or a pretext for sharing current objects directly.
- The branch already provides the operational concurrency MVP. A new MVP should test a new reuse hypothesis, for example owner-free immutable syntax payloads behind local wrappers, rather than repeat the existing two-JVM-to-one-JVM milestone.
- Shared caches need a semantic identity; engine/session registries need physical ownership identity and generation. These are different namespaces and must remain different types in the design.

### Gaps
- I inspected source and checked out the exact revision; I did not build Bazel or execute native acceptance. Recorded results below are branch evidence, not newly reproduced results.
- Native runtime is Linux-only; this research host is Windows. No Windows-native support claim follows from a successful source checkout.

## Which concrete design risks remain in the current source?

### Takeaway
The largest immediate architecture problems are runtime lifetime, startup serialization, ownership of asynchronous work, and implicit global capabilities. None requires replacing the incremental evaluator. Graph sharing is a separate identity/invalidation problem.

### Cited Findings
- **Closed engines retain runtime references.** `sharedEngines` retains `EngineSlot`, whose final `HostedEngine` retains dispatcher and a shutdown closure; `shutdownSharedEngine` closes registration but does not remove the slot or clear hosted references. `BugReport.MultiRuntime` independently keeps a strong list of engines with an add operation and no matching removal. Trigger: shut A down while B keeps the daemon alive. These references prevent reclaiming A's runtime by normal GC; the current two-lifetime-slot bound contains accumulation. Do not merely raise the slot cap. — [retained slot fields/map](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/CommandServer.java#L258-L284), [cleanup path](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/CommandServer.java#L412-L430), [crash registry](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/bugreport/BugReport.java#L120-L151)
- **Initialization blocks admissions on one daemon monitor.** Every shared request calls synchronized `getOrCreateEngine`. A new engine's `engineFactory.create` executes inside that synchronized method; existing engine requests cannot even take the present-slot fast path until construction completes. Trigger: slow B initialization while A submits another command. This is an admission/head-of-line latency risk, not a proven output-corruption bug. — [synchronized construction](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/CommandServer.java#L293-L324), [all requests call it](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/CommandServer.java#L368-L377)
- **Failed initialization is intentionally permanent quarantine.** Failed slots count against the two-engine cap and reject retries. Native engine ownership is process-lifetime; factory acquires it before opening directories/runtime and error cleanup closes directory handles but does not offer a release operation. This is fail-closed safety with poor churn/recovery, not evidence that the reservation should simply be released. — [failed slot/cap](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/CommandServer.java#L293-L324), [acquire before construction](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/runtime/BlazeRuntime.java#L1468-L1495), [process-lifetime API](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/SharedServerOwnership.java#L46-L47)
- **Directory fencing does not freeze running work.** `EngineDirectories` says explicitly that it is an admission check, not a snapshot or filesystem mutation lock. It compares physical directory identity at dispatch and after waiting for the command lock, with sticky fencing. Trigger needing qualification: rename/delete/recreate during an already-running action or asynchronous callback, or crash followed by surviving descendants. Existing dispatch checks alone cannot prove no writer touches a replacement tree. — [contract](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/EngineDirectories.java#L26-L33), [checks and shutdown rule](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/EngineDirectories.java#L60-L89)
- **RPC leases do not constitute a complete task-ownership model.** The registry tracks dispatch leases, and the runtime cleanup hook is invoked after they drain. The consolidated roadmap explicitly lists queued invocations, callbacks, materializers, action processes, future workers, and cache writes as needing ownership/accounting. This is a qualification gap; I did not prove a specific surviving writer in this audit. — [lease model](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/server/EngineRegistry.java#L93-L159), [lifecycle backlog](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/docs/jsgette/plans/multi-worktree-completion-roadmap.md#L110-L149)
- **Global safety is encoded as a denylist.** Runtime filters modules by class simple name and removes trace-profiler service; excluded modules include workers, dynamic execution, debugger, allocation/profiling, pressure/suspension, package metrics, and GC modules. A new/renamed module does not have to declare a concurrency capability to be admitted. Additional modules still run `globalInit` per engine. This argues for explicit owner/capability registration rather than assuming every future module is safe. — [denylist](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/runtime/BlazeRuntime.java#L1038-L1081), [module global init](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/runtime/BlazeRuntime.java#L1627-L1639)
- **Resource splits and compatibility are forced policy, not scheduling.** Each engine gets two jobs/loading threads/test jobs and estimated 2 CPU/1920 MiB; remote execution/cache, sandbox reuse and profiles are disabled; private repository-content cache and daemon disk action cache are forced. The policy uses final values ignoring overrides. One engine cannot elastically borrow the other engine's allocation through this policy, and the memory figure is not a JVM heap/RSS limit. — [complete policy](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/runtime/BlazeCommandDispatcher.java#L950-L1015)
- **Action-flight waiting has no fairness or rich result ownership.** The bounded set blocks while key is present or full, then uses `notifyAll`; it has no queue order, subscriber records, completed-result retention, or producer-task transfer. This is sufficient for the narrow synchronous successful-CAS contract but should not be lifted wholesale into a compiler service with different cancellation and failure semantics. — [registry implementation](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/src/main/java/com/google/devtools/build/lib/remote/SharedActionExecutionRegistry.java#L29-L74)

### Inferences
- Proposed explicit owner handles: `DaemonRuntime` owns compatible process services, scheduler, CAS, pure-result cache and crash registry; `EngineSession` owns evaluator/modules/physical output reservation; `InvocationScope` owns command state and every asynchronous task; `PayloadHandle` owns a frozen result without an engine back-reference. This is a design proposal derived from the risks, not an existing implementation.
- Recycling requires more than deleting a map entry: drain task scopes; join/cancel descendants and callbacks; close modules/executors/handles; unregister crash owner; release native reservation; atomically retire generation; only then admit a replacement. Failed cleanup remains quarantined.
- Reserve an INITIALIZING slot under a short registry lock, construct outside the lock, and publish READY atomically. Callers of the same slot await its future; unrelated ready engines should not wait for construction.
- For the next reuse MVP, avoid coupling lifecycle expansion, 4/8-engine admission, workers/remote parity, and a new graph store into one patch. Keep the existing two-engine restriction while proving one reuse boundary; correct unavoidable ownership defects before making disposal claims.

### Gaps
- No exhaustive mutable-static audit was performed. Existing denylist and documented restrictions establish where the audit must expand, not universal safety.
- Active-build crash descendants, disk-full/corruption, concurrent filesystem replacement, long churn, cross-namespace ownership, and asynchronous teardown require fault injection before release.
- Detailed Starlark compilation boundary and alternative incremental engines are covered by the sibling Skyframe/alternatives notes; this audit deliberately does not infer that source digest alone certifies current `Program`/AST reuse.

## What evidence exists, and what should carry into the next MVP?

### Takeaway
Recorded evidence supports a narrow native experiment with working concurrent actions and private outputs. Existing measurements establish neither general performance gains nor full-graph sharing. Preserve raw evidence and keep MVP correctness, subsequent benchmarks, and final product qualification separate.

### Cited Findings
- Native acceptance source checks one PID, two-engine admission bound, divergent build barrier/output isolation, equal digest executes once/materializes twice, warm A/B/A, glob additions/type changes/restoration, environment/configuration separation, test overlap, failure/cancel isolation, same-engine serialization, scoped shutdown and final daemon exit. The current harness expects 15 checks. — [barrier/action proof](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/tools/multiworktree/native_integration_test.py#L210-L245), [glob divergence](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/tools/multiworktree/native_integration_test.py#L247-L288), [remaining checks](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/tools/multiworktree/native_integration_test.py#L289-L417)
- Historical `native-acceptance.json` records 14 checks for the earlier binary, while the later payload report/roadmap records 15 after glob coverage. Do not collapse all validation counts into one full-suite result at the head. — [historical acceptance result](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/docs/jsgette/measurements/multi-worktree-native-mvp-2026-10-31/native-acceptance.json), [payload evidence](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/docs/jsgette/measurements/multi-worktree-native-mvp-2026-10-31/payload-reuse.json)
- Recorded Agent graph sample contains 80,847 nodes for each native engine (161,694 total), versus 80,837 for the vanilla control. The artifact expressly states private graph maps and `ram_usage_measured: false`. This proves node duplication in that sample, not physical memory or CPU attribution. — [graph ownership evidence](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/docs/jsgette/measurements/multi-worktree-native-mvp-2026-10-31/graph-ownership.json)
- The roadmap distinguishes operational native support, original immutable computation reuse, and full graph sharing. It reports 169.52 to 167.31 MiB two-engine live-object totals with payload interning, a single full-GC trial per candidate, not graph-retained memory or RSS. Original cold-action trials report a pair approximately 9.23% slower than one vanilla build, which is not the same comparison as pair throughput versus two independent concurrent servers. — [roadmap scope and result qualification](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/docs/jsgette/plans/multi-worktree-completion-roadmap.md#L14-L69)
- Existing plan already recommends typed pure compilation arguments, actual immutable bytes rather than potentially stale metadata digest, local dependency/freshness checks, completed immutable result publication, bounded cache, and delaying compiler single-flight until duplicate misses justify it. A new design should add an executable ownership/identity contract and chosen narrow slice, rather than merely relabel these intentions. — [original architecture contract](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/docs/jsgette/plans/multi-worktree-implementation-plan.md#L39-L89), [pure-stage feasibility](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/docs/jsgette/plans/multi-worktree-implementation-plan.md#L172-L191), [completed cache](https://github.com/JSGette/bazel/blob/4f4b44b5a2c1780cdbb0215c4556de39d0f0a995/docs/jsgette/plans/multi-worktree-implementation-plan.md#L241-L255)

### Inferences
- MVP acceptance should focus on an exact supported slice: same input gives equivalent result, every semantic input change misses, requesting-worktree diagnostics remain correct, private invalidation survives A/B/A and divergent/reconvergent edits, results cannot retain engines, and eviction leaves live readers valid. Instrument minimal counts/bytes/CPU needed to test the hypothesis; do not require a full benchmarking framework before a working vertical slice.
- Benchmark phase should decompose gains: independent-server baseline with same action cache/resources; shared host with reuse off; payload reuse on; next pure-stage cache on. Include one engine to catch tax, two engines with identical and divergent targets, cold analysis/hot actions, warm no-op, edits, and long churn. Test larger admission counts only after lifecycle/scheduler redesign.
- Polish phase follows measured value: explicit module capabilities, dynamic daemon budgets, recyclable sessions, invocation-aware diagnostics/profiling, disk GC, wanted commands/execution modes/platforms. None should be smuggled into the initial reuse MVP.

### Gaps
- All performance numbers in this note are recorded branch observations; no new benchmark was run.
- Broad real-workload benefits, deep retained object attribution, long-run bounded memory, and p95 behavior remain unestablished by this audit.
