# Git trees and independent edit overlays

## How should a draft and its immutable source view be represented?

### Takeaway

A Git commit can identify the common starting point. The tree named by that commit identifies its source contents. A draft can carry a small journal of edits and publish a new effective tree on capture. Two drafts can then refer to the same underlying blobs and directories regardless of who edited them or where they are checked out. This combines cheap editing with content equality at read time.

### Cited Findings

- A Git tree contains directory entries with names, modes and child object IDs. A tree can refer to a blob or another tree. Commits add parentage, authorship and a message to a root tree. File contents can occur at several paths using the same blob object. [Git Internals, Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)
- A linked worktree gives a checkout its own HEAD and index while sharing repository data with other linked worktrees. A worktree is an ordinary, editable representation. Its directory name alone says nothing about which bytes a later reader will see. [git-worktree](https://git-scm.com/docs/git-worktree)
- A private index can be selected with `GIT_INDEX_FILE`. `git read-tree <commit>` loads its tree into that index. `git update-index --cacheinfo` records an existing blob and its path and mode. `git write-tree` emits the ID of a tree from a fully merged index. Ordinary disk edits must be read or supplied separately. This flow permits a new tree without making a commit or changing the user's staged content. [Git environment](https://git-scm.com/docs/git#Documentation/git.txt-GITINDEXFILE) [git-read-tree](https://git-scm.com/docs/git-read-tree) [git-update-index](https://git-scm.com/docs/git-update-index) [git-write-tree](https://git-scm.com/docs/git-write-tree)
- Git's cache-tree index extension records directory tree IDs for spans of the index. A path change invalidates the relevant directory and ancestors. An unchanged subtree can be skipped when building a tree or comparing with an existing tree. This is an existing example of incremental construction. It gives no general guarantee about how cheaply arbitrary edits can be *discovered* in a checkout. [gitformat-index, Cache tree](https://git-scm.com/docs/gitformat-index#_cache_tree)
- Jujutsu illustrates a different user-facing choice. Most of its commands snapshot changed working-copy contents into a replacement working-copy commit. Its policy for automatically including new files is configurable, and ignored files are excluded from automatic tracking. The useful precedent is that evolving drafts can publish immutable revisions before a person decides to make a durable commit. [Jujutsu working copy](https://docs.jj-vcs.dev/latest/working-copy/)
- OverlayFS demonstrates two different directory semantics. Deleting a lower entry requires a whiteout. A replacement directory can be marked opaque so that none of the lower directory's children appear in its listing. An ordinary upper directory can instead merge its children with the lower directory. This distinction is useful in a portable logical model, independently of the Linux mount implementation. [Kernel OverlayFS documentation](https://docs.kernel.org/filesystems/overlayfs.html#whiteouts-and-opaque-directories)

### Inferences

- Distinguish three names. **Base commit** records provenance. **Overlay handle** names an editable draft and may point to a new revision after each edit. **Effective tree ID** names specific visible entries and contents under an agreed source policy. Two different base commits can have the same tree ID. Two different journals can produce the same effective tree ID. If code reads revision metadata (e.g. stamping), that observation remains a separate build input.
- **Materialized linked worktrees** are a good editing interface and isolated reference result. Each tool can read native paths, and A's write does not alter B's checkout. Discovering equality requires inspecting or snapshotting the selected workspace contents. Creating a directory per worktree does not intrinsically assign an immutable read view to a build or make the in-memory analysis graph shareable.
- **A sparse path map or typed edit journal** describes what the user changed. A path entry can replace a file (contents and executable intent), create a symlink (target text), or delete an entry/subtree. Directory patches distinguish “inherit other children” from “replace the children entirely.” An ancestor removed or replaced by a non-directory masks all lower descendants. Rename can be represented as remove plus add with the same object ID for the moved contents. Optional rename metadata helps editing/merging, while tree reads depend on the resulting names and contents. A simple hash of a raw series of edit operations identifies the recipe and can distinguish identical results.
- **A persistent content-addressed tree** is a useful read representation. Applying known edits rebuilds affected directory nodes up to the root. Other child IDs can be reused. Starting a new logical draft from an already captured root can be a single root reference. A new checkout, a copied flat Git index, a scan of an ordinary directory and first-use hydration each have separate costs. For k edits of depth at most d, at most roughly k×d distinct containing directories need new representations. Cost also includes newly hashed file bytes, entry encoding and lookup. Git encodes a directory's child list as one tree object, so changing one entry in a wide directory can re-encode many siblings. A contiguous flat index and an application-owned trie also have different costs. Tree-based representation does not imply total update time proportional to depth alone.
- **Use the map and the tree at different times**. An editor-managed stream can append or batch a few edits, apply them to a persistent tree, then atomically advance the overlay's root. A build retains the previous root and its reachable objects. No global order between A and B is needed. A fork begins from either the base root or any captured draft root. Moving a draft to a different base is a separate replay or three-way merge and can conflict.
- The logical layer needs operations such as `lstat`, `readFile`, `readlink`, and `listDir` on one pinned view. For example, a delete followed by recreation of a directory must not resurrect old children unintentionally. A full replacement tree handles this by omission. A live sparse map needs ancestor shadowing, tombstones and a defined directory merge rule.

### Gaps

- A stable immutable result says nothing about atomicity during capture. Enumerating changes and hashing files in an externally editable directory can observe different instants. Supplying one known batch of immutable edit data, capturing a filesystem snapshot or establishing an explicit writer/capture boundary are different ways to define the input. Retries on detected changes are an optimization, not a proof of an atomic cut across arbitrary external writers. Even an editor-owned journal needs a definition of which external edits were imported.
- Actual capture, physical sharing and storage costs depend on source-tree width, overlay size, ignored/untracked policy, object-store retention and the editing workflow. A directory tree ID equality proof establishes equality of its encoded entries assuming collision resistance. It does not measure runtime, heap or OS-level data-page sharing.

## What can be demonstrated using Git alone?

### Takeaway

A disposable Git experiment produced three distinct draft roots from a single base and retained a common `lib/` subtree. It showed that later edits can change A's current revision while old A and sibling B remain independently readable.

### Cited Findings

- **Observed locally, Git 2.52.0.windows.1, SHA-1 repository.** Base commit `12896084b565` held `app/main.c` containing `base\n`, `app/old.h` containing `old\n` and `lib/math.c` containing `lib\n`, all mode 100644. The base root was `5d21ff5af33f`. A1 changed the working bytes of `app/main.c` to `edit A\n` and produced `8dc443585048`. B1 deleted `app/old.h` and added `app/new.h` containing `new\n`, producing `18887a497761`. A2 applied a later edit of `later A\n` and produced `34bba8875930`. Reading A1 after A2 still returned `edit A\n`, and B1 still returned `base\n` for main.c. All four roots referenced `3fc53550c019` for `lib/`. No draft commit was created. Git commands used below have the documented semantics. [git-hash-object](https://git-scm.com/docs/git-hash-object) [git-read-tree](https://git-scm.com/docs/git-read-tree) [git-write-tree](https://git-scm.com/docs/git-write-tree)
- **Observed local isolation.** Before A1, the real index had been given `staged A\n` for main.c while the working file held `edit A\n`. The private A index used bytes read from disk. At the end HEAD still named the same base commit, `git show :app/main.c` still printed `staged A`, and SHA-256 of the complete real index file was identical before and after. B1's app listing contained `main.c` and `new.h`. The base/A1 list contained `main.c` and `old.h`. [git-status, index and working tree](https://git-scm.com/docs/git-status) [git-ls-tree](https://git-scm.com/docs/git-ls-tree)
- **Reproduction steps.** In an empty scratch Git SHA-1 repository, disable autocrlf, add the three LF-terminated base files above, then commit `base`. (For the exact commit hash, set both identities to `Overlay Study <experiment@example.invalid>`, both dates to `2000-01-01T00:00:00+00:00`, and use a normal `base\n` message. Tree IDs are independent of identity/date.) Stage `staged A\n`, then write `edit A\n` to the file. For A and B separately use a fresh path outside the checkout as `GIT_INDEX_FILE`. Run `git read-tree HEAD` for each. Hash replacement bytes with `git hash-object -w --stdin --no-filters`, and for each put run `git update-index --add --cacheinfo 100644,<blob>,<path>`. To remove B's header, supply `0 <40 zeros><TAB>app/old.h<LF>` to `git update-index --index-info`. After each batch run `git write-tree`. Inspect each `<tree>:lib`, `<tree>:app/main.c`, and `git ls-tree --name-only <tree>:app`. Repeat the put for A2. The preceding hashes are prefixes of actual outputs, from one Windows run with controlled edit batches. No performance timing was gathered. [git-update-index](https://git-scm.com/docs/git-update-index) [git-ls-tree](https://git-scm.com/docs/git-ls-tree)

### Inferences

- Subtree equality can prove whole areas unchanged without descending into them. Distinct roots say only that some encoded entry differs. An observer that merely lists names/kinds in `app/` sees the same response in base and A1 even though A1's `app` subtree ID changed. B1's result differs for that same observation. File digests, names/type listings and negative lookups have different reuse boundaries.

### Gaps

- The example passes a known edit set and explicit typed bytes. It tests tree construction and rendering through Git. It does not test automatic change discovery, projection onto every host, arbitrary builds or cross-overlay evaluation reuse.

## Which semantics must remain explicit across Linux, macOS and Windows?

### Takeaway

An immutable logical tree can travel between hosts. An ordinary checkout is a projection of that tree under filesystem and Git settings. A source model intended to reproduce an existing native build must define what each tool actually sees, even when Git regards the checkout as clean.

### Cited Findings

- Git's index uses repository-relative path names with `/` separators. The encoding is otherwise unspecified apart from byte restrictions. File modes encode regular files, symlinks and gitlinks, and distinguish normal from executable regular files. [gitformat-index](https://git-scm.com/docs/gitformat-index)
- Git can normalize line endings and call clean/smudge filters. Git LFS stores a pointer in Git while the working copy can contain externally stored data. A gitlink specifies a submodule commit and cannot describe its uncommitted working files. [gitattributes](https://git-scm.com/docs/gitattributes) [Git LFS](https://git-lfs.com/) [gitsubmodules](https://git-scm.com/docs/gitsubmodules)
- Git has distinct settings for executable bits, case-insensitive volumes, macOS filename decomposition and materializing logical symlinks as ordinary files containing link text. Apple documents both case-sensitive and case-insensitive APFS variants and normalization-insensitive behavior for relevant macOS releases. Win32 documents reserved device names and path rules. [git-config](https://git-scm.com/docs/git-config) [Apple File System FAQ](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/FAQ/FAQ.html) [Windows file naming rules](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)
- Git garbage collection can prune unreachable objects. Keeping the hexadecimal ID in application memory is separate from anchoring it in the object store's reachability/lifetime protocol. [git-gc](https://git-scm.com/docs/git-gc)

### Inferences

- Preserve repository-relative path components and original spelling in the logical source tree. Translate paths and validate collisions at materialization using the target volume's semantics. Globally lowercasing or applying Unicode normalization would merge distinctions present in some source trees. Native views of both `Foo.h` and `foo.h` may be impossible on one volume. Detect that, or use a declared portable naming subset in the research example. A single OS name alone is an insufficient proxy for volume behavior.
- Pick one coherent domain for the study: **repository-object bytes**, with an explicit projection policy, or **effective source bytes observed by tools**, with the resolved kind, mode and contents captured in a view. If the latter is required, the canonicalized Git blob ID alone can be insufficient even for tracked unchanged files. If a checkout transforms just base files or staged files, applying a raw-worktree-byte overlay to canonical blobs creates an inconsistent mixed view. The plain-text LF fixture avoids that ambiguity intentionally.
- For a controlled comparison, ordinary directories containing simple names and normalized fixture bytes work on all three systems in principle. Byte-stable regular files with explicit edits make a good initial research scope. Arbitrary native filenames, symlinks pointing outside the tree, repository filters, empty directories, ignored build-visible files, recursive dirty submodules and metadata such as mtimes are separate decisions. Git's normal index-and-write-tree workflow does not preserve arbitrary filesystem metadata or ordinary empty working directories.
- An application-owned object store can hold ephemeral draft contents and pin reachable objects while a build reads them. A Git-backed alternative needs a lifetime strategy such as private refs in an isolated store, with base objects retained if imported by reference. An alternate index alone protects staged state but does not isolate the Git object database. Avoid a production conclusion that a write to the user's object database is necessary.

### Gaps

- Only the controlled Git experiment ran locally on Windows. Current host-specific behavior for a proposed materializer should be tested on its actual target volumes. Other aspects such as overlay merge conflicts or outside-tree symlinks need no commitment to answer the immediate research question about choosing a model.
